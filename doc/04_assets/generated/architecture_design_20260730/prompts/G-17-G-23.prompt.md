## G-17 Data Performance Chain

### 1. 图编号与图名

【图编号】G-17  
【图名】Data Performance Chain

### 2. 图的目的与核心问题

请生成一张用于正式架构设计说明书的数据处理性能链路图。

本图必须回答：

- Probe 到页面可见结果之间，吞吐、排队、Lag、状态处理、Checkpoint、Sink 和投影延迟分别出现在哪里；
- 如何用同一事件标识关联采集时间、处理时间、提交时间和页面可见时间；
- 哪些位置需要采集性能证据，而不是填入未经实测的性能数值。

### 3. 架构时态与系统边界

这是目标态性能观测参考架构，不是当前生产性能实绩。右上角只显示状态徽标 `TARGET DESIGN` 和 `NOT EXECUTED`。

平台定位为园区及中小型政企网络流量安全分析平台。控制面复杂度适中，但数据面可独立扩展。不得表现多地域、多云、服务网格或超大规模微服务集群。

### 4. 16:9布局

使用16:9横版画布，1920×1080或更高分辨率。

采用“左到右主链＋底部观测轨道”：

- 上方主链从 `01 Probe` 依次流向 `10 Web UI`；
- `04 Flink Src`、`05 State`、`06 Compute`、`07 Sink`组成一个浅橙色Flink处理区域；
- `11 Perf Obs`置于底部中央，以细虚线采集关键阶段遥测；
- 指标标记放在线段附近，不添加独立指标节点；
- 避免交叉箭头，保留充足留白。

### 5. 节点白名单

- `01 Probe`
- `02 Ingest`
- `03 Kafka`

### 6. 允许连线

只允许以下关系：

- `01 Probe → 02 Ingest`：异步流量批次；
- `02 Ingest → 03 Kafka`：异步事件写入；
- `03 Kafka → 04 Flink Src`：异步消费；
- `04 Flink Src → 05 State`：Flink内部处理；
- `05 State → 06 Compute`：状态计算；
- `06 Compute → 07 Sink`：批量输出；
- `07 Sink → 08 Projection`：异步事实或投影更新；
- `10 Web UI → 09 Query API`：查询请求；

- `Produce`
- `Lag`

- `Sink`

- 禁止 `Web UI` 直接连接Kafka、Flink或Projection；
- 禁止Flink参与普通用户、权限、规则审批等控制面CRUD；
- 禁止把一次HTTP请求画成同步写入多个分析存储；
- 禁止把 `Perf Obs` 画成控制业务状态的组件；
- 禁止填写吞吐、P95、P99、10×100Gbps、512Mpps等未经同候选实测的数值；
- 禁止把设计目标表现为当前已通过；
- 禁止新增云厂商、数据湖、AI平台、服务网格或白名单外组件。

### 3. 架构时态与系统边界

- `07 Candidate — 08 Test Case`：中性无箭头Trace关系；
- `07 Candidate — 09 Perf Failure`：中性无箭头Trace关系；
- `08 Test Case ⇒ 10 Evidence Run`：双线证据引用；

- `07 Candidate → 10 Evidence Run`：红色虚线 `STALE` 失效关系；
- `07 Candidate → 11 Arch View`：红色虚线 `STALE` 失效关系。

### 7. 禁止关系

- 禁止把Arch View或ADR当作系统真实运行状态的唯一事实来源；
- 禁止Test Case或Perf Failure不绑定Candidate；
- 禁止Evidence Run缺少Candidate身份；
- 禁止用`latest`结果替代不可变候选证据；
- 禁止把可移动Tag等同于不可变Digest；
- 禁止把人工检查缺失、工具不可用或证据缺失标记为PASS；
- 禁止ADR与Capability、Feature或变更反馈完全脱节；
- 禁止用运行时调用箭头绘制普通Trace关系；
- 禁止新增CI平台、云项目管理、工单厂商或白名单外组件；
- 禁止把目标态表现为当前已通过。

### 9. 验收标准

- 节点恰好12个，名称、编号和大小写完全正确；
- Capability到Feature、OpenAPI/Proto Event、Domain Repo、Data Policy和Candidate的追溯链完整；
- Test Case与Perf Failure都必须绑定Candidate；
- Test Case与Perf Failure都必须形成Evidence Run证据；
- Evidence Run必须进入Arch View，Arch View必须追溯到ADR；
- ADR必须反馈到Feature；
- Candidate变化必须使Evidence Run与Arch View显式STALE；
- 普通Trace使用无箭头线，不得误画成运行时调用；
- 不把Arch View当作事实来源，不使用latest或可移动Tag替代候选身份；
- 不出现白名单外组件、文字或关系，阅读者30秒内能够说明“需求—契约—实现—数据—候选—测试—证据—架构—ADR”的治理闭环。
