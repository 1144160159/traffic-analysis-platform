## 3. 架构时态与事实边界

- 采用单一时态：`目标责任架构`。
- 图中不使用“已投产”“已高可用”“全部验收通过”等措辞。
- 历史功能主链证据只用顶部状态说明表达，不把历史时点运行数字混入节点。
- `10×100Gbps`、`512Mpps`、端到端P95、准确率、误报率、RTO、RPO、HA和第三方验收均不写入图内。
- 当前仓库中存在组件或Manifest，不等于目标安全、投影、可观测、备份恢复与故障演练已经完成。

## 4. 16:9总体布局

使用16:9横版，建议3840×2160视觉密度，采用“六层主架构＋右侧运营闭环＋底部横向能力带”。

### 4.1 顶部标题区

- 左上：主标题；
- 标题下方：副标题；
- 右上：`目标责任架构`状态徽标；
- 状态徽标下方：`历史功能主链有证据｜专项指标待验收`。

### 4.2 中部主架构区

从上到下六层：

1. 用户与外部协同层；
2. 交互访问层；
3. 业务控制层；
4. 采集与实时分析层；
5. 多模数据与证据层；
6. 运维与治理支撑层。

右侧单独设置“安全运营闭环”纵向区域，由下游告警事实回到规则／模型更新，再返回Kafka／Flink运行时。

### 4.3 排版规则

- 每层使用独立浅色泳道背景和清晰中文层名；
- 控制面与数据面通过颜色和泳道分开；
- 多存储使用同一大容器内的六个独立职责卡片，不能合成无语义“数据库”；
- Flink采用一个大容器，内部列出九类处理能力，不把每个Job画成独立微服务；
- Go控制面采用一个大容器，内部列出主要业务域，不暗示一页一服务；
- 右侧闭环使用顺时针箭头，避免穿越中部主链；
- 连接使用正交折线，避免交叉、遮挡和穿过节点。

## 6. 允许连线与方向

### 6.1 用户访问与认证

- `安全值班员／安全研判员／平台管理员／测试验收人员 → Web UI`
- `Web UI ↔ APISIX网关`：同步命令或查询；
- `企业身份源 ↔ 身份与权限 ↔ APISIX网关`：认证；
- `APISIX网关 ↔ Go业务控制面`：同步命令或查询。

### 6.2 控制面事务与Outbox

- `Go业务控制面 ↔ PostgreSQL权威状态`：同步事务与有界查询；
- `Go业务控制面 → 异步任务与通知`：异步任务；
- `PostgreSQL权威状态.Outbox → Kafka事件总线`：异步领域事件，线旁标注`Outbox`；
- `Go业务控制面 ↔ ClickHouse／OpenSearch／NebulaGraph／Redis`：有界查询；
- `Go业务控制面 ↔ MinIO`：授权后的对象上传、读取或短期签名引用。

### 6.3 采集与实时数据面

- `网络镜像／TAP → Rust探针`：镜像流量；
- `资产／日志／用户事件 → Ingest接入或Kafka事件总线`：多源事件；
- `Rust探针 → Ingest接入`：批量流／会话／PCAP索引；
- `Rust探针 → MinIO`：PCAP对象；
- `Ingest接入 → Kafka事件总线`：版本化流事件；
- `Kafka事件总线 → Flink实时计算`：异步消费；
- `Flink实时计算 → ClickHouse`：事实与聚合；
- `Flink实时计算 → OpenSearch`：检索投影，按目标责任表达；
- `Flink实时计算 → NebulaGraph`：关系投影，按目标责任表达；
- `Flink实时计算 ↔ MinIO`：Checkpoint、Savepoint、模型或对象引用；
- `Flink实时计算 → Kafka事件总线`：派生事件或运行回执，使用回流外轨。

不得画 `Flink → Redis` 为主要事实写入链。

### 6.4 安全运营闭环

- `ClickHouse／OpenSearch／NebulaGraph → 告警研判`：查询结果或投影；
- `告警研判 → PCAP／图谱取证`；
- `PCAP／图谱取证 → TP／FP反馈`；
- `TP／FP反馈 → 白名单／规则复审`；
- `TP／FP反馈 → MLOps训练评估`；
- `白名单／规则复审 → 规则／模型更新`；
- `MLOps训练评估 → 规则／模型更新`；
- `规则／模型更新 → 部署与运行回执`；
- `部署与运行回执 → Kafka事件总线`：规则或模型更新事件；
- `部署与运行回执 → Flink实时计算`：运行应用与回执；
- `告警研判／取证／反馈／部署结果 → 合规与证据包`：审计证据；
- `Go业务控制面 ↔ 外部响应／通知`：受控意图、任务和回执。

### 6.5 横向支撑

- 主组件到 `可观测` 使用细紫色虚线，表示遥测采集；
- `契约治理` 横向支撑 Probe、Ingest、Kafka、Flink、Go控制面；
- `安全内建` 横向支撑入口、服务、消息、数据与对象；
- `部署治理` 横向支撑应用、流处理和数据组件；
- `恢复治理` 关联Kafka、Flink、多存储与对象；
- `验收证据` 汇聚候选、测试、运行、故障和回滚证据。

横向支撑线应弱化，避免覆盖业务主链。

## 9. 禁止关系与禁止表达

- 禁止Web UI直连任何数据库、Kafka、Flink或MinIO；
- 禁止Probe直写PostgreSQL、ClickHouse、OpenSearch或NebulaGraph；
- 禁止把Kafka画成页面查询接口；
- 禁止把一次HTTP请求画成同步写入六种存储；
- 禁止OpenSearch、NebulaGraph或Redis反向覆盖PostgreSQL权威状态；
- 禁止Redis被表现为业务事实权威；
- 禁止MinIO被表现为权限或业务状态真源；
- 禁止Flink承担用户、权限、审批、规则编辑等普通CRUD；
- 禁止PostgreSQL被表现为所有原始流量的唯一事实库；
- 禁止把外部响应画成平台已经实现的全自动阻断；
- 禁止增加Data Lake、Spark、Service Mesh、多云、多地域双活、超大型SOC、云厂商产品或白名单外核心组件；
- 禁止填入未经同候选实测的吞吐、时延、准确率、副本、RTO、RPO或HA数字；
- 禁止写“全部验收通过”“生产安全已达标”“目标已实现”。
