## 2. 方案亮点(方法论层面)

1. **双计划源不建两套系统**(§2.1):只建两种"计划编译入口",共用 Topic/状态机/报告——这是最容易走偏的地方,方案一开始就掐死了。
2. **六类显式结果**(§8.2):每输入必须落 POSITIVE/NEGATIVE/INCONCLUSIVE/INCOMPATIBLE/ERROR/NOT_RUN 之一,且明确"NEGATIVE 仅在完整性通过时可用于无威胁结论"——直接消除"无输出=安全"这一检测系统最危险的误报源。
3. **口径警告**(§3.2):明文警告"总体 Accuracy 不能代替预警准确率",并要求 Recall/F1 同步报告防止"通过减少告警虚增精度"。这是真懂检测评测的人写出来的。
4. **测试集一次冻结**(§2.1/§9.1):阈值只能在验证集调整,测试集不得反复调参;明文禁止"训练集结果/验证集最佳点/演示样本/告警命中率"冒充最终结论。
5. **错误防治前置**:E2E-04(损坏/Hash 不符在采集前失败)、E2E-06(不兼容 Preflight 阻断)、E2E-07(越权 403+审计)把失败路径放进首版验收矩阵,而不是只测快乐路径。
6. **回滚策略配"禁止操作"栏**(§13.3):删除已物化 Plan/Run、覆盖旧列含义、静默复用不兼容 UID/state 等被显式禁止——与本仓库 `agent.md` 全局约束(删除须确认)同向。
7. **风险表 R1-R8 与控制措施一一对应**,尤其 R4(无输出被当作 NEGATIVE)与 R8(用已知攻击门冒充未知攻击能力)是最常被忽视的两条。
8. **交付目录建议**落在 `contracts/analysis/`、`data/manifests/`、`tests/analysis/`、`evidence/analysis/<candidate>/`——与仓库既有 `contracts/authz/` 惯例一致,可直接执行。

## 4. 评审意见(建议先修订再启动)

### 4.1 指标口径:补两处冻结(P0)

- **Recall 没有数字下限**。方案要求 Recall"同步报告并满足项目签字下限",但签字下限未在本版冻结。在 Precision ≥95% + FPR <5% 双门下,最省事的通过方式是"只告警最有把握的极少数样本"——Recall 可能崩到 30% 仍"签字通过"。建议 W0 补:Recall ≥ 90%(或 PR-AUC ≥ 0.95)作为 G7 的第三道硬门,并冻结"测试集正样本最小基数"(建议 ≥ 200)。
- **样本基数未冻结**。95%/5% 在小样本上极易虚高(10 个正样本里 1 个误报 = Precision 91%)。建议 dataset_manifest.json 增加每 split 的正/负样本数与攻击家族分布下限。
- **术语双名注意**:方案"误报率"用 FPR(FP/(FP+TN)),与"预警准确率"(TP/(TP+FP))分母不同,二者不可换算——方案已分开定义,但建议在 W0 合同里加一行"False Alarm Rate = 1 - Precision"的等价提醒,防止执行时混用。

### 4.2 权限契约:拆细 analysis 域 scope(P0)

§0.2 的最小权限基线要求五类动作分别授权,而 m10 契约目前只有 `analysis:read`/`analysis:write`。建议在 W0 内把 m10 增加:

```
analysis:run:view / analysis:run:cancel / analysis:run:retry
analysis:report:download / analysis:evidence:export
analysis:plan:create / analysis:plan:approve
```

其中"计划审批与计划编辑分离"直接对应现有 admin/super_admin 与 analyst 的角色边界,不需要引入新角色体系,只需扩展契约 operations + 注册 scope(注意同步 `registered_scopes` 计数)。

### 4.3 端到端矩阵:补两条失败路径(P1)

- **E2E-13 质量门 FAIL 的完整路径**:冻结测试集上故意注入一个低于门的候选,验证"Run 终态 + 报告明示'工程链路完成,质量门未通过'"、不显示为成功。目前 E2E-12 只覆盖报告生成失败,未覆盖质量门失败这一更重要的业务路径。
- **E2E-14 数量守恒审计**:构造阶段丢输入的场景,验证"特征成功+不兼容+错误+未执行=阶段输入"守恒校验能报警且阻断 DETECTION_AGGREGATE。

### 4.4 与既有文档的关系(P1)

`doc/07_alignment/` 下已有《核心主链代码级设计-v1》《统一调度中心实现设计 卷A/卷B》《业务主链组件映射-v1》等。本 PDF 应在其首页加一段"文档谱系":本方案是执行层纪律文件,代码级设计是结构文件,两者冲突时以本方案的合同冻结为准——否则执行中会出现"设计文档说 X、执行方案说 Y"的裁决真空。

### 4.5 与五本设计书分析的呼应(记录用)

- 方案把"阈值只在验证集调、测试集一次冻结"制度化,与《GoF》"效果记录取舍代价"、《大话》"封装变化点"同源;
- "MachineSummary 不可变 + 人读报告异步派生"是 Command/审计思想的延伸,与仓库 `analysis` 域的信封化命令一致;
- §2.1"先合同、后迁移、再消费者、最后生产者和 UI"正是《破译WebUI》"网格先于线框图"的工程版,值得在团队内宣讲。

3. **DetectionResult 与 RunClosureManifest 两个具名合同对象**应在 W0 内补入代码(目前是行为存在、名字缺失),与五阶段收据枚举一起冻结。
