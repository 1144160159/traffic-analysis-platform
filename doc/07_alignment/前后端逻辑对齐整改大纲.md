# 前后端逻辑对齐整改大纲

版本：2.0  
日期：2026-07-30  
适用仓库：`traffic-analysis-platform`  
依据：仓库 `agent.md`、`doc/` 主线文档、当前源码与部署清单、《前后端逻辑对齐分析.pdf》和《架构设计.pdf》。  
登记规模：54项canonical功能整改、48项canonical技术整改，共102项；完整报告采用严格Unicode `Script=Han`十万汉字口径。

## 一、整改总目标

本次整改不是一次“大重写”，也不是把所有数据库和接口揉进一个需求。总目标是建立一套可以长期证明前后端、业务、API、数据和验收一致性的工程机制：

1. 用户可见功能只增不减。已有路由、Tab、查询参数、按钮、深链、API、响应字段、权限、审计事件和导出格式均应冻结为兼容基线。
2. 页面上的每个查询和动作都能追踪到稳定 `feature_id`、`control_id/action_id`、API `operation_id`、领域命令或查询、权威数据源、事务、事件、异步投影和最终 UI 状态。
3. 页面不再通过猜测任意数组、任意数字、中文文案或硬编码常量弥补后端契约缺口。
4. PostgreSQL、ClickHouse、OpenSearch、NebulaGraph、Redis、Kafka、MinIO职责清晰，控制面 CRUD 不同步写多个异构存储。
5. 性能整改以基线和复测为前提，所有结论都有浏览器、API、数据库、消息链路或流处理证据。
6. 每次只整改一个功能纵切片或紧密功能簇，避免一次性改全站导致兼容、数据回填和回滚失控。
7. 最终形成机器可校验的契约清单、差异矩阵、迁移记录、回滚包和验收证据，而不是只形成文字说明。

## 二、核心问题树

### 2.1 契约层问题

- `routeManifest.tsx`、`pageApiPlans.ts`、页面契约、`services/api.ts`、Go DTO、Proto、APISIX 路由、SQL Schema分别描述相同能力，但缺少统一校验。
- Proto承担跨语言消息契约，但无法完整描述REST工作台的过滤、分页、治理字段和聚合视图。
- 资产模块已出现Proto `page_size/page_token`、REST `limit/offset`、前端同时发送多套参数、PG治理字段远多于Proto的明确漂移。
- 部分页面动作计划声明了端点，但运行时被适配到另一种业务操作，形成“计划契约存在、真实业务结果不存在”。
- 权限作用域在页面、动作计划、后端校验和认证可签发目录之间没有强制一致性。

### 2.2 页面与业务语义问题

- 部分专题动作根据中文按钮文案正则推断 `action`，文案变化可能改变业务命令。
- 通用快照适配器存在从任意嵌套数组推断表格、从任意数字推断KPI、用fallback覆盖零值或生成业务ID的风险。
- 页面加载请求扇出，同一屏的KPI、图、表和证据可能来自不同时间点。
- 个别按钮显示“导出、关联、保存、阻断”等强业务语义，实际只写备注、本地存储或排队记录。
- 页面能够打开不等于功能闭环；需要区分“已受理、同步中、投影完成、业务执行完成、失败可恢复”。

### 2.3 数据与性能问题

- PostgreSQL列表存在精确 `COUNT(*) + OFFSET`、多列 `%ILIKE%`、高频JSONB正则与数组展开。
- 资产批量绑定在消费批次后可能逐条查写和逐条写事件，事务和审计原子性不足。
- 服务启动时执行 `InitSchema`，与部署SQL在类型、空值约束和字段演进上存在漂移。
- ClickHouse告警列表使用 `alerts_latest FINAL`、精确总数、OFFSET、JSON聚合再由Go反序列化。
- 多张CH Distributed表仍使用 `rand()` 分片；是否造成跨分片扇出需按真实查询分布验证。
- NebulaGraph工作台会加载整租户节点与“relation”记录，再在Go中筛选；ClickHouse兼容路径同样整租户扫描后过滤。
- OpenSearch仍有 `from/size` 查询路径，同时需要核对实际索引是否遵循版本化模板、alias和生命周期。
- 同步HTTP业务链如果同时更新PG、CH、OS和图数据库，将带来部分成功、延迟尾部和无法原子回滚的问题。

### 2.4 验收与治理问题

- 现有真实API、浏览器和回归证据较强，但功能回归不能替代性能、检测质量、HA和第三方验收。
- 很多页面动作只验证HTTP 2xx或数据库新增行，没有验证最终业务效果。
- 缺少全仓库 `removed_routes/actions/api_operations/response_fields/scopes/audit_events` 自动差异门禁。
- 缺少统一的性能基线数据集、查询指纹、并发模型、压测窗口和对照报告。
- 缺少异步投影的lag、失败率、DLQ、重放和对账SLO。

## 三、总体整改方法论

### 3.1 六层契约模型

| 层级 | 真源职责 | 禁止事项 |
|---|---|---|
| Feature Contract | 业务语义、页面状态、动作、权限、状态机、字段口径、数据归属、审计、验收 | 不描述为纯UI文档 |
| OpenAPI | REST请求、响应、分页、错误码、operation_id、兼容版本 | 不由前端和Handler各自手写不同DTO |
| Protobuf | gRPC和Kafka事件消息、字段演进、跨语言兼容 | 不强行承载所有页面聚合视图 |
| Versioned Migration | PG/CH/OS/Nebula物理结构、索引、回填、回滚 | 服务启动不得随意改生产Schema |
| Generated Client | Go/TypeScript客户端、枚举、错误类型、序列化 | 不保留手工复制的漂移类型 |
| Page View Model | 页面纯展示结构、格式化、局部交互状态 | 不重新解释业务统计口径或生成业务值 |

### 3.2 八阶段闭环

#### 阶段A：冻结现有能力基线

自动枚举页面、路由、深链、Tab、URL状态、控件、动作、API、字段、错误码、权限、审计、状态机、数据库对象、Topic和验收能力，形成 `baseline-manifest`。任何后续变更必须生成兼容性差异。

#### 阶段B：建立纵向功能矩阵

读功能按以下链路建模：

```text
页面状态
→ query_id
→ API operation_id
→ domain query
→ authoritative/read model
→ SQL/nGQL/DSL
→ 字段与KPI口径
→ snapshot_version/as_of
→ 页面状态
```

写功能按以下链路建模：

```text
control_id
→ stable action_id
→ API operation_id
→ domain command
→ 校验/权限/状态机
→ PG业务事务
→ audit_log
→ outbox_event
→ Kafka topic/key/schema
→ CH/OS/Nebula幂等投影
→ operation/projection status
→ UI最终状态
```

#### 阶段C：数据归属与一致性分级

- PG：主数据、可变业务状态、权限、审批、任务、审计、outbox。
- CH：流、会话、特征、检测事实、时间序列和分析投影。
- OS：全文、日志、模糊和跨字段搜索投影。
- NebulaGraph：实体关系、邻居、路径和多跳遍历投影。
- Kafka：领域事件、流数据、顺序、解耦、重放。
- Redis：不作为业务权威；可重建缓存允许淘汰，限流、幂等和租约等协调状态进入独立可靠性域。
- MinIO：PCAP、报告、模型和证据制品。

一致性分为：强一致业务事务、读己之写、最终一致投影、分析快照、离线报告。页面必须显示对应语义。

#### 阶段D：采集性能基线

在修改前固定数据规模、时间窗、并发、筛选条件和运行版本，采集HAR、trace、API分位数、PG `EXPLAIN ANALYZE`、CH `query_log`、OS `_profile`、Nebula `PROFILE`、Kafka lag、Flink backpressure/checkpoint、Redis命中率和对象存储吞吐。

#### 阶段E：按证据选择优化

把根因分类为 `contract-drift`、`frontend-fanout`、`N+1`、`deep-offset`、`exact-count`、`jsonb-scan`、`FINAL`、`wrong-sharding`、`sync-multi-write`、`full-tenant-graph-load`、`missing-batch`、`missing-index`、`serialization`、`lock-contention`、`connection-pool`、`projection-lag`，每项只在证据支持后进入实现。

#### 阶段F：逐功能纵向切片

每个切片严格执行：冻结旧行为测试、更新Feature Contract、更新OpenAPI/Proto、生成类型、增加migration、实现repository/service/handler、实现outbox/consumer/projection、更新typed UI、补齐测试和证据。

#### 阶段G：兼容迁移与灰度

采用additive schema、双读/双写或影子读、离线回填、校验、灰度切流和明确回滚。禁止直接删除旧端点、旧表、旧字段或旧深链。

#### 阶段H：验收与关闭

必须同时通过兼容、契约、权限、租户隔离、业务状态机、数据一致性、浏览器交互、性能回归、故障恢复和证据完整性门禁，才能关闭一个 `feature_id`。

## 四、整改步骤

1. 建立整改基线分支与只读快照，记录commit、镜像、DDL、Topic、索引、路由和验收资产。
2. 编写inventory工具，从前端、APISIX、Go路由、Proto和数据库定义提取机器清单。
3. 建立feature registry和action registry，为用户可见能力分配稳定ID。
4. 形成契约差异矩阵，标出P0语义错误、P1闭环缺失、P2技术债。
5. 形成数据归属矩阵和同步/异步一致性矩阵。
6. 先完成W1护栏和P0止血：消除告警／专题语义替换、修复消息与对象静默丢失、收敛scope，并为专题建立最小真实执行器。
7. 选择资产模块作为首个完整样板，验证契约、migration、bulk upsert、cursor、统计投影和typed View Model。
8. 扩展告警报告、告警—战役关联、任务进度、批量分派和CH／OS读取链。
9. 扩展专题统一快照、动作目录、审批补偿和报告对象化。
10. 改造图谱邻居与路径查询、持续投影、保存视图和服务端导出，保留旧workbench响应适配层。
11. 治理OS索引/alias、Kafka envelope、Flink sink和缓存键。
12. 建立全站页面快照规范，减少扇出并统一 `snapshot_version/as_of/data_mode/source_status`。
13. 执行数据回填、影子比对、灰度切换和故障注入。
14. 产出逐功能证据包，并刷新项目级完成度审计。

## 八、实施波次

| 波次 | 周期建议 | 重点 | 退出条件 |
|---|---:|---|---|
| W0 基线 | 2周 | inventory、feature registry、契约diff、性能采集脚本 | 基线可重复，六类removed差异可计算 |
| W1 护栏与最小闭环 | 3周 | 消息／对象止血、scope、告警真实最小端点、专题live schema与最小executor | 已知P0不再语义替换且有最小真实结果 |
| W2 资产纵切＋关键路径P0加固 | 3周 | 资产原子写入、cursor、发现；并行加固消息／对象／权限／告警／专题 | 资产闭环，W1／W2关键路径P0具备可运营证据 |
| W3 告警扩展 | 4周 | 多格式报告、活动、任务进度、批量、CH／OS性能 | 告警完整体验与最终效果通过 |
| W4 专题扩展 | 4周 | 完整快照、动作目录、审批补偿和报告对象化 | mock关闭后专题全链通过 |
| W5 图谱与投影 | 3周 | 查询下推、持续投影、保存／导出和权限 | 图查询预算和对账达到批准门槛 |
| W6 存储迁移 | 3周 | CH V2、OS alias、Kafka/Flink、Redis/MinIO治理 | 数据对账与回滚演练通过 |
| W7 整改专项验收 | 2周 | 全量回归、性能、混沌、回滚、证据归档 | P0/P1按批准范围关闭；不替代项目外部验收 |

该顺序相对附件“契约→资产→图→告警→OS→页面扇出”的一般建议做了风险驱动调整：告警语义替换、专题伪成功和数据丢失属于P0，必须在W1提供最小真实闭环；资产样板在W2并行；图谱性能影响仍需E2基线，故放在W5。完整报告第5卷记录同一顺序和退出条件。

24周表是平台护栏和四条主样板的核心关键路径，不等同固定人力下关闭全部102个ID。其余全域工作包依据资源情景并行；若要求24周关闭全部批准P0／P1，W0必须补充扩展团队、外部窗口和逐包排期，未纳入当期的ID保持OPEN或BLOCKED而不从清单删除。
